02 / Under the surface

The interface is
the shallow end.

Three working parts of this page: an X-ray over a real screen, the order state machine that screen sits on, and whatever the GitHub API reports while you read it.

X-ray

Move the light across the creator panel

Move the cursor across the screen to look through it. The drawing underneath is the schema and the guards that answer each click. Pick a marker to read what sits there. On a phone, or with reduced motion, the two layers sit side by side instead.

The four counters

Net sales, orders, customers and products resolve against orders, payments and inventory rows. Stock is bounded by database checks, available >= 0 and reserved <= available, so an oversell fails in Postgres before it fails in the UI.

Revenue attributed, not estimated

The seven-day chart is built from analytics_events joined through content_products, which is what lets a reel claim the money it earned instead of a number someone guessed at.

The attention queue

Three lists a creator acts on: orders to fulfil, variants running low, and setup steps left. They read the same orders.status and inventory rows as the counters, so the panel cannot call a store healthy while it is out of stock.

Recent orders

Each row is an orders record with its order_items and payments row. Status changes append to order_activity_log, so a disputed order can be replayed instead of argued about.

One search box

Products, orders and customers from a single field, because a creator looking for a customer should not have to know which table they live in.

Two separate worlds

Creator identity lives in platform_users and creator_settings. Staff identity lives in platform_staff_members and platform_staff_sessions. A creator credential and a staff credential are never the same row.

State machine

How an order survives

Eleven states, sixteen legal moves. Pick one. The wires below are drawn from the same transition table the API enforces, so an assistant tool call and a human click pass the same guard.

  • PENDING_PAYMENT

    An order exists and the stock question is settled, but no money has moved. Two doors out: PAID or CANCELLED. Nothing on this path can print a label.

  • PAID

    Set inside one function. It takes a transaction-scoped advisory lock plus a row lock, returns ALREADY_CONFIRMED on a second call, and rejects anything where the captured amount does not equal orders.total_minor. A valid signature only proves the payment id was real; the amount check is what proves the money matches the order.

  • PROCESSING

    Creator-side work begins. Still reversible: CANCELLED and REFUNDED both remain legal, because a packed order can be stopped and a paid one can be walked back.

  • PACKED

    The last state a creator can still cancel from. After this the parcel is the carrier's problem, and the only exits are SHIPPED or a cancellation that the model refuses.

  • SHIPPED

    A shipments row carries the provider and tracking code, which is what the thermal label printed from. Forward moves are delivery or a return request; there is no route back to CANCELLED.

  • OUT_FOR_DELIVERY

    One exit and no branches. The last ambiguous stretch of an order's life is deliberately the narrowest.

  • DELIVERED

    Terminal for the seller's obligations. The customer's only remaining door is RETURN_REQUESTED.

  • CANCELLED

    No exits. Four states can reach it, and each arrival is checked against this table rather than against a form field.

  • RETURN_REQUESTED

    Customer intent, not a refund. Reaching REFUNDED requires the parcel to come back through RETURNED first.

  • RETURNED

    Goods are back with the creator. REFUNDED is the only way out, which is what keeps a return from becoming a discount.

  • REFUNDED

    No exits. The money trail sits in refunds and the ledger entries behind it, so a refund can be reconciled against the payout that funded it.
